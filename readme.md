# 树型区域信息结构需求梳理

## 一、核心问题分析

### 传统递归查询的痛点

常规树型表设计（`parent_id` 外键模式）在军核IoT场景下存在明显瓶颈：

- **深度查询代价高**：查询某节点的完整子树需要 N 次递归 SQL，层级越深越慢
- **路径拼接低效**：生成完整路径（如 `机电产业园\监控室\内监控室\火灾监控`）需要从叶子逐层向上回溯
- **并发压力大**：IoT场景下设备状态频繁更新，树结构读操作密集，传统方案数据库压力大
- **实时性要求高**：军核系统对区域信息的准确性、时效性要求远高于普通系统

## 二、推荐数据结构方案

### 方案对比

| 方案 | 适用场景 | 查询子树 | 查询路径 | 插入/移动节点 | 适合军核IoT？ |
|------|---------|---------|---------|------------|------------|
| **Parent ID**（传统） | 简单少层级 | 递归，慢 | 递归，慢 | 容易 | ❌ |
| **Closure Table**（闭包表） | 读多写少、深层级 | O(1) | O(1) | 中等 | ✅ 推荐 |
| **Materialized Path**（物化路径） | 读多、层级不太深 | LIKE查询 | O(1) | 容易 | ✅ 可选 |
| **Nested Set**（嵌套集） | 极少修改的静态树 | O(1) | 复杂 | 极难 | ❌ |

### 推荐：Closure Table + Materialized Path 双字段方案

```
区域节点表 (area_node)
├── id                  -- 节点ID
├── name                -- 节点名称
├── parent_id           -- 直接父节点（保留，用于直接子节点查询）
├── path                -- 物化路径，如 "/1/5/12/34/"（快速模糊查询）
├── path_name           -- 名称路径，如 "机电产业园/监控室/内监控室"
├── depth               -- 层级深度（根=0）
├── sort_order          -- 同级排序
├── node_type           -- 节点类型（园区/楼栋/房间/设备点位等）
└── is_active           -- 软删除标志

闭包关系表 (area_closure)
├── ancestor_id         -- 祖先节点ID
├── descendant_id       -- 后代节点ID
└── depth               -- 两节点间距离（0=自身）
```

这个双表方案的核心优势：

- **闭包表**：任意祖孙关系一次 JOIN 即可查出，无需递归
- **物化路径**：`path_name` 字段直接存储完整路径名称，读取路径为 O(1)
- **`parent_id`保留**：查直接子节点极快，无需走闭包表

## 三、三大核心查询的实现逻辑

**① 查询直接子节点**
```sql
SELECT * FROM area_node WHERE parent_id = :nodeId AND is_active = 1
```
直接索引命中，极快。

**② 查询完整子树（所有后代）**
```sql
SELECT n.* FROM area_node n
JOIN area_closure c ON n.id = c.descendant_id
WHERE c.ancestor_id = :nodeId AND c.depth > 0 AND n.is_active = 1
```
闭包表一次 JOIN，无递归。

**③ 查询完整路径名称**
```sql
SELECT path_name FROM area_node WHERE id = :nodeId
-- 结果直接返回："机电产业园\监控室\内监控室\火灾监控"
```
直接读字段，O(1)。

## 四、增删改的可靠性考量（军核重点）

### 新增节点
- 插入 `area_node` 同时，将父节点的所有闭包记录复制一份指向新节点
- 需在**事务**中完成，保证闭包表与主表一致性
- 同步更新 `path`、`path_name`、`depth` 字段

### 删除节点（高风险操作）
- **禁止物理删除有子节点的节点**，必须前端拦截 + 后端双重校验
- 推荐**软删除**（`is_active=0`），军核系统历史数据需可追溯
- 级联软删除子树时，闭包表保留但查询时过滤 `is_active`

### 移动节点（最复杂操作）
- 需删除旧闭包关系、重建新闭包关系，同步更新整个子树的 `path`、`path_name`
- 必须在**分布式锁 + 事务**中执行，防止并发移动冲突
- 操作前记录**变更日志**，支持回滚审计

## 五、前端组件设计要点

### 组件职责划分

```
TreeManager（容器组件）
├── AreaTree（树展示）         -- 虚拟滚动，支持大量节点
├── NodeDetail（节点详情）     -- 查看完整路径、节点属性
├── NodeEditor（新增/编辑）    -- 表单，含父节点选择器
├── NodeMover（移动节点）      -- 拖拽或弹窗选择目标位置
└── BreadcrumbPath（面包屑）   -- 展示当前节点完整路径
```

### 前端可靠性要点

- **懒加载**：默认只加载根节点和第一层，展开时按需请求子节点，避免全树加载压垮接口
- **乐观更新 + 回滚**：操作后立即更新UI，若接口失败自动回滚，给用户即时反馈
- **操作防重**：新增/移动/删除按钮操作期间 loading 锁定，防止重复提交
- **危险操作二次确认**：删除节点（尤其含子树时）必须强确认弹窗，展示影响范围
- **路径面包屑**：选中节点时始终展示完整路径，避免用户在深层级迷失

## 六、整体稳定性建议

| 层面 | 建议 |
|------|------|
| **数据库** | 闭包表的 `(ancestor_id, descendant_id)` 建联合唯一索引；`path` 字段建前缀索引 |
| **缓存** | 树结构读多写少，适合 Redis 缓存全树或热点子树，变更时精准失效 |
| **并发** | 写操作加分布式锁（节点级），防止同一节点并发修改导致闭包表脏数据 |
| **审计** | 所有增删改操作记录操作日志（操作人、时间、变更前后快照），军核合规要求 |
| **降级** | 缓存穿透时降级走数据库，数据库异常时前端展示上次缓存的树结构并提示只读模式 |

---

## 七、开发建议顺序

1. **先定数据库表结构**，确认 Closure Table + 物化路径双方案
2. **封装后端 TreeService**，统一管理增删改查，对外暴露语义化接口
3. **前端封装 `useAreaTree` Hook**，统一管理树数据状态、懒加载、缓存
4. **开发 TreeManager 组件**，各子组件通过 Context 共享树状态
5. **联调测试**，重点测移动节点、并发写、大数据量懒加载三个场景
